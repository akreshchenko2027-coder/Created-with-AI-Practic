# ПР6. RAG-помічник за власною базою знань

Матеріали до шостої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР6.pdf`, виданому до заняття.

## Задача коротко

У ПР5 пошук повертав фрагменти документів, і читав їх користувач. Тут їх читає **мовна модель**: за питанням клієнта помічник знаходить кілька фрагментів бази знань магазину «Сузірʼя», віддає їх моделі разом із інструкцією й повертає відповідь **із джерелами**, на які вона спирається. Якщо відповіді в базі немає — помічник прямо про це каже, а не вигадує. Це і є retrieval-augmented generation: пошук з ПР5 плюс модель із ПР3–ПР4, зʼєднані шаром, який вирішує, що модель побачить і чому можна вірити в тому, що вона повернула.

Наприкінці — перевірка на наборі питань із відомими відповідями й розбір помилок на два кошики: помилки пошуку і помилки генерації.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Пошук, індекс, RAG-конвеєр, інтеграція з моделлю та вебсторінка |
| `docs/` | Та сама колекція документів, що в ПР5; опис — у `docs/README.md` |
| `ingest.py` | Побудова індексу — той самий, що в ПР5 |
| `requirements.txt` | Залежності роботи: ПР4 + ПР5 разом |
| `.env.example` | Зразок налаштувань: доступ до моделі, ембедінги, збирання контексту |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, колекція, модель ембедінгів, пробний запит до мовної моделі |
| `eval/` | 15 прикладів питань, скрипт прогону й класифікація помилок |

```
app/
├─ main.py                веб-рівень: сторінка, /api/status, /api/ask
├─ documents.py           читання документів і поділ на фрагменти
├─ embeddings.py          локальні вектори multilingual-e5
├─ index.py               косинусний пошук і збереження індексу
├─ keyword.py             пошук BM25
├─ retrieval.py           злиття пошуку, фільтри й бюджет контексту
├─ llm.py                 клієнт і запит до мовної моделі
├─ schema.py              контракт і перевірка відповіді
├─ rag.py                 конвеєр: знайти → зібрати → спитати → перевірити
└─ templates/index.html   сторінка: питання, відповідь, джерела, «що бачила модель»
```

`documents.py` ділить Markdown за заголовками й абзацами, `embeddings.py` кодує запити та фрагменти, `index.py` зберігає й ранжує вектори, а `keyword.py` виконує пошук BM25. `retrieval.py` об'єднує обидва пошуки, завжди прибирає архівні й внутрішні документи та вкладає фрагменти в бюджет контексту. `schema.py`, `llm.py` і `rag.py` перевіряють JSON-відповідь, викликають модель і підтверджують її посилання на джерела. Вебсторінка показує відповідь, джерела, службові дані й фрагменти, які бачила модель.

## Початок роботи

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
copy .env.example .env
python check_env.py
```

Для macOS і Linux активація середовища — `source .venv/bin/activate`, копіювання — `cp .env.example .env`.

Перед запуском:

1. **Ключ доступу** — перенесіть `LLM_API_KEY` із `.env` папки `pr4` (або `pr3`) у `.env` цієї роботи. Не надсилайте ключ у чат і не додавайте його до git.
2. **Налаштування пошуку** — якщо у ПР5 ви обрали іншу модель ембедінгів або інший поділ на фрагменти, перенесіть значення `EMBEDDING_MODEL`, `CHUNK_SIZE` і `CHUNK_OVERLAP` у `.env`.
3. **Індекс** — збудуйте його командою `python ingest.py`. Код пошуку вже є в `app/`; переносити файли з ПР5 не потрібно.

**Запустіть `check_env.py` заздалегідь.** Він перевіряє пакети, налаштування, завантаження ембедінгів і доступ до мовної моделі. Без робочого API-ключа застосунок запуститься, але не зможе генерувати відповіді.

Запуск застосунку з папки `pr6`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 і поставте питання за документами.

## Що очікує сторінка

При відкритті сторінка викликає `GET /api/status` і показує, чи збудовано індекс. Питання — `POST /api/ask` з обʼєктом `{"question": "...", "filters": {"product": "Вега S"}}`; фільтри можуть бути порожніми.

У відповідь сторінка очікує `{"answer": "...", "found": true, "sources": [...], "retrieved": [...], "model": "...", "elapsed": {"retrieval": 0.04, "generation": 1.9}, "usage": {...}}`. Кожне джерело — `{"ref": 1, "score": 0.03, "source": "файл.md", "metadata": {...}, "text": "..."}`; оцінка — рангова оцінка об'єднаного пошуку, а не ймовірність правильності. `retrieved` — фрагменти в тому вигляді, у якому їх бачила модель.

## Як влаштована реалізація

| Де | Що зробити |
|---|---|
| `app/documents.py`, `embeddings.py`, `index.py`, `keyword.py` | Розбиття, локальні E5-вектори, збереження індексу й BM25 |
| `app/retrieval.py` | Об'єднання пошуку, фільтри доступу, відбір фрагментів і бюджет |
| `app/schema.py`, `llm.py`, `rag.py` | Схема JSON, виклик моделі, перевірка джерел і конвеєр |
| `app/main.py` | Сторінка та HTTP-помилки для некоректного вводу, відсутнього індексу й збоїв моделі |
| `eval/run_eval.py` | Прогін набору питань і збереження контексту для класифікації помилок |

Початковий поріг семантичної схожості — `0.35`, а в контекст ідуть до чотирьох фрагментів. Це стартові параметри, а не виміряні оптимуми: перевірте їх на своєму наборі й змінюйте лише один параметр за раз.

## Перевірка відповідей

Скопіюйте `eval/questions.example.json` у `eval/questions.json` і за потреби змініть або доповніть власні 12–15 питань. Після побудови індексу й налаштування ключа запустіть:

```bash
python eval/run_eval.py
```

Скрипт зберігає контекст, відповідь, джерела, час і токени після кожного питання у `eval/results.json`. Якщо API перерве серію через ліміт, продовжте її з паузою між запитами: `python eval/run_eval.py --resume --pause-between 15`. Поля `review` заповнюються вручну: перевірте факти, ґрунтованість відповіді та посилання, а кожну помилку віднесіть до пошуку або генерації. Для порівняння однієї зміни, наприклад кількості фрагментів, виконайте другий прогін окремим файлом:

```bash
python eval/run_eval.py --context-chunks 2 --output eval/results-k2.json --pause-between 15
```

Порівняйте метрики й заповніть `eval/findings.md` за висновками обох прогонів. Результати й власні питання локальні та не комітяться.

## Чекліст самоперевірки

- [ ] На питання з відповіддю в базі помічник відповідає за документами й посилається на джерела, які справді містять сказане.
- [ ] На питання без відповіді в базі помічник прямо каже, що інформації немає, і не вигадує.
- [ ] Внутрішні документи не потрапляють до моделі, коли питає клієнт, — і це забезпечує код, а не користувач.
- [ ] Контекст збирається з обмеженої кількості фрагментів у межах бюджету; кожен фрагмент позначено джерелом.
- [ ] Відповідь моделі перевіряється за схемою; посилання на джерела перевіряються кодом.
- [ ] Сторінка показує відповідь, позначку «знайдено / немає», джерела, фрагменти, які бачила модель, час пошуку й генерації, токени.
- [ ] Застосунок не падає: без індексу каже, що робити; порожнє питання, збій моделі, невалідна відповідь дають зрозумілу помилку.
- [ ] Модуль пошуку не знає про модель, модуль моделі — про індекс, веб-рівень — ні про що з цього.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Перевірку проведено на 12–15 питаннях; помилки поділено на помилки пошуку й помилки генерації; одну зміну перевірено окремо; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
