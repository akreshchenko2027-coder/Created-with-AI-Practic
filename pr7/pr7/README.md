## Задача коротко

Постачальники надсилають магазину «Сузірʼя» рахунки на оплату — сканами, фото з телефона, знімками екрана. Бухгалтерія переписує з них реквізити й суми в реєстр платежів. Ви будуєте застосунок, у якому це робить **мультимодальна модель**: читає зображення рахунку й повертає заданий набір полів у структурованому вигляді. А далі — те, що робить його придатним для грошей: **код** перевіряє вилучене за схемою і програмними правилами (контрольні суми IBAN і ЄДРПОУ, арифметика рядків і ПДВ, дати, покупець, довідник постачальників) і вирішує, чи можна документ пропустити без людини.

Наприкінці — прогін якісних і навмисно погіршених зразків і відповідь на питання, скільки помилок моделі ловлять ваші правила, а скільки проходять тихо.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Каркас застосунку |
| `samples/` | 9 рахунків гарної якості, 18 погіршених варіантів, правильні значення в `expected.json`; опис — у `samples/README.md` |
| `reference/` | Реквізити своєї компанії й довідник постачальників — для правил |
| `degrade.py` | Погіршити зображення самостійно: розмиття, масштаб, контраст, поворот, обрізання, шум, JPEG |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок локальних налаштувань Ollama й обмежень на зображення |
| `check_env.py` | Перевірка Python, пакетів, `.env`, зразків і пробного запиту із зображенням |
| `eval/` | Перевірка на зразках: якісні проти погіршених |

У перевірках усі суми рахуються через `Decimal`: сума позиції округлюється
до копійок методом half-up, суми підсумків мають збігатися до копійки,
для ПДВ допуск — одна копійка. Будь-яка помилка правила веде на ручну
перевірку; документ, визначений не як рахунок, відхиляється.

```
app/
├─ main.py                веб-рівень: сторінка, /api/samples, /api/extract, зразки як статичні файли
├─ images.py              перевірка й підготовка зображення
├─ llm.py                 запит до мультимодальної моделі
├─ schema.py              контракт і перевірка відповіді моделі
├─ rules.py               програмні правила й читання довідників
├─ extraction.py          конвеєр і рішення auto / review / reject
└─ templates/index.html   сторінка: зображення, рішення, проблеми, поля, позиції
```

Застосунок приймає зразок або завантажене зображення, готує його, звертається до мультимодальної моделі, перевіряє відповідь за схемою і правилами та показує рішення з причинами. У цій роботі використано Gemma 3 4B через локальну Ollama. Для запуску потрібні залежності, встановлена Ollama із завантаженою моделлю та локальний `.env`; Gemini API key не потрібен.

### Безкоштовний запуск локально через Ollama

Це рекомендований і перевірений варіант запуску цієї роботи: запити до моделі обробляються на компʼютері, без Gemini API та без хмарної API-квоти.

1. Встановіть [Ollama](https://ollama.com/download) і дочекайтеся, поки локальний сервіс запуститься.
2. У PowerShell з папки `pr7` завантажте мультимодальну модель:

   ```powershell
   ollama pull gemma3:4b
   ```

3. Скопіюйте `.env.example` у `.env`. У зразку вже вказано локальні налаштування:

   ```env
   LLM_BASE_URL=http://localhost:11434/v1/
   LLM_API_KEY=ollama
   LLM_MODEL=gemma3:4b
   ```

`ollama` тут — технічне значення для OpenAI-сумісного клієнта; локальна Ollama його ігнорує. Це не Gemini API key. Модель працює на вашому компʼютері; плати за API немає, але потрібні місце на диску й ресурси компʼютера. На CPU 4B-модель може обробляти документи повільно. Файл `.env` потрібен локально для налаштувань, але він уже виключений із Git: не додавайте його до здачі й не надсилайте ключі.

**Запустіть `check_env.py` заздалегідь.** Він надсилає моделі невелике зображення з числом — покаже, чи приймає обрана модель зображення, скільки триває відповідь і скільки токенів коштує навіть крихітна картинка.

Запуск застосунку з папки `pr7`:

```bash
uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000 — сторінка покаже зразки; розбір запрацює, коли локальна Ollama запущена і модель завантажена.

## Результат оцінювання та обмеження

Оцінювання виконано локально моделлю Gemma 3 4B на 29 зразках, включно з двома власними. Базовий прогін дав точність полів 54,94% і 25/87 правильних критичних полів; прогін зі стороною зображення до 1200 px — 52,90% і ті самі 25/87 критичних полів. Зменшення зображення не покращило результат. В обох прогонах було 0 тихих помилок: перевірки спрямували сумнівні документи на ручний перегляд, але це не означає, що модель безпомилкова.

Детальні таблиці, порівняння та контрольні приклади наведено у [`eval/findings.md`](eval/findings.md). Результат демонструє роботу мультимодального вилучення й контрольного конвеєра, але точність недостатня для автоматичного перенесення реквізитів без людини.

**Про відповідність критеріям:** у доступному описі завдання йдеться про мультимодальну модель; у цій реалізації це локальна Gemma через Ollama, а не Gemini. Якщо у виданому викладачем PDF або окремих вказівках прямо вимагається Gemini чи конкретний хмарний сервіс, цей варіант треба попередньо погодити з викладачем. Сам факт локального запуску не дозволяє гарантувати оцінку.

Для здачі додайте код, цей README та звіт оцінювання. Не додавайте `.env`, API-ключі чи локальні файли `eval/results/` із сирими відповідями. Якщо критерії вимагають продемонструвати власні зразки, додайте лише безпечні для передачі зображення й відповідні правильні значення; не використовуйте справжні рахунки чи персональні дані без дозволу.

## Що очікує сторінка

Розбір — `POST /api/extract` з файлом у полі форми `image`. У відповідь сторінка очікує `{"decision": "review", "reasons": [...], "document": {...}, "issues": [...], "image": {...}, "model": "...", "elapsed": {...}, "usage": {...}}`. `document` — поля, як їх повернула модель після перевірки схемою, будь-якої вкладеності; перший список обʼєктів у ньому сторінка показує як таблицю позицій. Кожна проблема — `{"field": "supplier.iban", "rule": "iban_checksum", "message": "...", "severity": "error"}`; поле з таким шляхом сторінка підсвічує; комірку позиції — за шляхом на кшталт `items.1.amount`, де індекс рядка рахується з нуля. `image` — `{"original": {"width", "height", "bytes"}, "sent": {...}}`. Веб-рівень збирає цей обʼєкт з `extraction.Result` функцією `result_to_dict` — якщо зміните склад `Result`, змініть і її, і сторінку; вони ваші.

## Що реалізувати

| Де | Що зробити |
|---|---|
| `app/images.py` → `prepare` | Перевірити, що файл — придатне зображення; врахувати орієнтацію; зменшити й перекодувати для моделі |
| `app/schema.py` → `output_schema`, `validate` | Контракт відповіді: заданий набір полів, типи, відсутні значення |
| `app/llm.py` → `get_client`, `build_messages`, `extract` | Інструкція для вилучення, запит із зображенням, виклик, перевірка, збої |
| `app/rules.py` → `check` | Програмні правила: IBAN, коди, арифметика, дати, покупець, довідник, обовʼязкові поля |
| `app/extraction.py` → `decide`, `process` | Конвеєр і рішення `auto` / `review` / `reject` з причинами |
| `app/main.py` → `api_extract` | Обробити збої: порожній чи завеликий файл, не зображення, збої моделі, невалідна відповідь |
| `eval/` | Прогін зразків, власні зразки, порівняння з `expected.json`, одна зміна, висновки |

Рішення, які стоять за кожним пунктом, перелічені в розділі 2 практичної роботи — продумайте їх до того, як писати код.

## Чекліст самоперевірки

- [ ] Значення, якого в документі немає або якого не видно, повертається як відсутнє, а не вигадується.

- [ ] Рішення `auto` / `review` / `reject` ухвалює код за результатами перевірок, а не модель; причини показано.
- [ ] Текст у документі, адресований «системі обробки», не впливає на рішення.
- [ ] Сторінка показує рішення, проблеми, поля, позиції, розміри зображення до й після підготовки, час, токени.

- [ ] Модуль зображень не знає про модель, модель — про правила, веб-рівень — ні про що з цього.
- [ ] Ключ не потрапив ані в код, ані в репозиторій.
- [ ] Прогнано всі зразки й щонайменше два власні; порівняно з правильними значеннями по варіантах; пораховано тихі помилки; одну зміну перевірено окремо; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
