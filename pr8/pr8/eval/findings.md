## Порівняння ліміту звертань

Прогін виконано з `TOOL_MAX_ROUNDS=2`; інші налаштування ті самі, що й у базовому прогоні.

| Показник | Ліміт 3 (база) | Ліміт 2 |
|---|---:|---:|
| Питань | 21 | 21 |
| Текстові відповіді | 18 | 11 |
| Зупинки за лімітом | 1 | 8 |
| Збої без відповіді | 2 | 2 |
| Середні звертання для записів із usage | 2,26 | 1,84 |
| Середні prompt tokens для записів із usage | 4 258 | 3 072 |

За ліміту 2 цикл частіше не встигає сформулювати відповідь після пошуку й наступного інструмента. У q07 виконано пошук і перевірку 7 одиниць товару, але розрахунок доставки не встиг виконатися; зупинився також q08, хоча для нього потрібні пошук і один розрахунок. За ліміту 3 q07 встиг отримати всі три результати, але все одно вичерпав останнє звертання до текстової відповіді. Нижчий ліміт заощаджує в середньому близько 1 186 prompt tokens, ціною меншої кількості завершених відповідей.

## Прогін із відмовами сервісу

Прогін виконано з `SHOP_FAILURE_RATE=0.3` та базовим `TOOL_MAX_ROUNDS=3`.

```powershell
python eval/run_eval.py --failure-rate 0.3 --output eval/results-failure-30.json
```

| Показник | Результат |
|---|---:|
| Питань | 21 |
| Текстові відповіді | 18 |
| Зупинки за лімітом | 1 (q07) |
| Збої моделі без відповіді | 2 (q10, q15) |
| Виклики інструментів | 23 |
| Відмови магазину `unavailable` | 4 із 23 (17,4%) |

Відмови сервісу спостерігались у q02, q05, q07 і q20. У q02, q05 та q20 модель пояснила тимчасову недоступність. У q07 збій розрахунку доставки після успішного пошуку й перевірки залишку завершився повідомленням про недоступність сервісу, без вигаданої ціни. Частка фактичних відмов за один запуск може відрізнятися від 30%, оскільки перевірка використовує випадкові відмови. q04 (`not_found`) і q11 (`policy`) — очікувані бізнес-результати, а не недоступність сервісу.

Не трактувати `error` у runner автоматично як помилку магазину: звіряти поле `error`, `calls` і `stopped`. Збої без відповіді в q10 та q15 не містять помилок інструменту; це відповіді моделі.
