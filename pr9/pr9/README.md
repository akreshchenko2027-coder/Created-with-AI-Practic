# ПР9. Побудова багатоетапного AI workflow

Матеріали до девʼятої практичної роботи. Повний текст завдання, критерії приймання й контрольні запитання — у документі `ПР9.pdf`, виданому до заняття.

## Задача коротко

У ПР8 помічник сам вирішував, які інструменти викликати й у якому порядку. Звернення «хочу повернути пилосос із замовлення 10412» щодня обробляється тими самими кроками: зрозуміти, про що просять, знайти замовлення, перевірити правила, оформити заявку, відповісти. Тепер послідовність задає **ваш код**, а модель виконує лише ті кроки, де потрібне розуміння мови: розбір звернення й відповідь клієнтові.

Заявка на повернення чи скасування змінює дані, тому workflow **зупиняється перед нею**, доки оператор не підтвердить. Пауза може тривати годину, а застосунок за цей час можуть перезапустити, тож стан звернення **зберігається на диску**. Кожне звернення має обмеження — кроки, час, токени — і доходить до кінцевого стану.

Наприкінці — той самий набір звернень обробляється **агентом із ПР8**, і два підходи порівнюються.

## Що в цій папці

| Файл | Призначення |
|---|---|
| `app/` | Реалізація workflow, API, інструментів і порівняльного агента |
| `shop/` | Сервіс магазину — той самий, що в ПР8, **готовий**, змінювати не потрібно |
| `requirements.txt` | Залежності роботи |
| `.env.example` | Зразок налаштувань: доступ до моделі, обмеження агента й workflow, каталог стану, поведінка сервісу магазину |
| `check_env.py` | Перевірка середовища: Python, пакети, `.env`, сервіс магазину, перенесені модулі ПР8, каталог стану, пробний structured output |
| `eval/` | Порівняння workflow й агента на наборі звернень |

```
app/
├─ main.py                веб-рівень: сторінка, /api/requests, /api/runs, /api/runs/{id}/decision
├─ workflow.py            керовані кроки, переходи, обмеження й підтвердження
├─ state.py               стан звернення: Run, Step
├─ store.py               атомарне збереження стану на диску
├─ schema.py              схеми розбору звернення й відповіді
├─ tools.py               інструменти магазину й контроль доступу
├─ llm.py                 клієнт моделі й structured output
├─ assistant.py           агент із циклом викликів ПР8
└─ templates/index.html   сторінка: звернення, журнал кроків, черга оператора

shop/
├─ service.py             функції сервісу
└─ data/                  клієнти, замовлення, товари, склад, тарифи доставки
```

Сторінка дає обрати клієнта (це заміняє вхід у кабінет), надіслати звернення на обробку workflow або агентом, переглянути журнал кроків і використання обмежень, чергу оператора з кнопками «підтвердити» й «відхилити» та перелік звернень.

## Початок роботи

1. **Середовище:**

   ```powershell
   python -m venv .venv
   .\.venv\Scripts\Activate.ps1
   pip install -r requirements.txt
   Copy-Item .env.example .env
   ```

   Для macOS і Linux активуйте середовище командою `source .venv/bin/activate` і скопіюйте налаштування через `cp .env.example .env`. Для локальної Ollama використовуйте `http://localhost:11434/v1` і встановлену модель `qwen3:4b`. Секрети до репозиторію не додавайте.

2. **Модулі з ПР8** уже перенесені в `app/`: інструменти, цикл агента й OpenAI-сумісний клієнт. Для workflow додано виклик моделі без інструментів зі structured output.

3. **Перевірка:**

   ```powershell
   .\.venv\Scripts\python.exe check_env.py
   ```

   Скрипт перевіряє залежності, інструменти ПР8, доступність сервісу й structured output. Він також показує, якщо пробна модель вигадала номер; workflow окремо відкидає номер, якого немає у зверненні.

Запуск застосунку з папки `pr9`:

```powershell
python -m uvicorn app.main:app --reload
```

Далі відкрийте http://127.0.0.1:8000.

Workflow виконує розбір і перевірку звернення, читає дані тільки через інструменти, визначає маршрут і зупиняється перед поверненням або скасуванням. Після рішення оператора умови перевіряються ще раз. Стан звернення записується в `RUNS_DIR` атомарно; перезапуск не прибирає чергу. Подвійне підтвердження не повторює дію, а повторне повернення перевіряється за заявками сервісу. Якщо перезапуск стався під час самої зміни, неоднозначну дію автоматично не повторюють.

Для локальної Ollama `app/llm.py` використовує її `/api/chat` з вимкненим режимом міркувань: так structured output Qwen не витрачає ліміт відповіді на прихований текст аналізу. Для інших OpenAI-сумісних адрес залишається клієнт OpenAI SDK.

## Що очікує сторінка

Нове звернення — `POST /api/requests` з `{"customer_id": "C-1003", "text": "...", "mode": "workflow"}`. Для `workflow` у відповідь сторінка очікує стан звернення — `Run` з `app/state.py`, перетворений функцією `run_to_dict`: `run_id`, `status`, `route`, `steps`, `pending`, `decision`, `reply`, `stopped`, `usage`, `elapsed` і `limits`. Кожен елемент `steps` — `Step`: `{"n": 1, "name": "parse", "kind": "model", "status": "ok", "detail": "...", "input": ..., "output": ..., "elapsed": 0.9, "usage": {...}}`. Типи `model`, `tool`, `code`, `human` і відомі статуси сторінка позначає кольором, інші показує як є. Для `agent` — те саме, що в ПР8 (`answer_to_dict`).

Черга оператора — `GET /api/runs?status=awaiting_approval`; якщо ваш статус очікування називається інакше, змініть константу `WAITING_STATUS` на сторінці. Для дії, що чекає підтвердження, сторінка показує поля `pending.summary`, `pending.tool`, `pending.arguments`, `pending.grounds`, якщо вони є, і решту як є. Рішення оператора — `POST /api/runs/{run_id}/decision` з `{"approve": true, "comment": "..."}`.

## Реалізація

| Де | Що зробити |
|---|---|
| `app/tools.py`, `app/llm.py`, `app/assistant.py` | Перенесені інструменти й агент ПР8; для Ollama structured output викликається через локальний API |
| `app/schema.py` | Схеми розбору, вибору товару й відповіді; перевірка результатів |
| `app/workflow.py` | Маршрути, кроки, повторна перевірка, підтвердження, контроль обмежень і відновлення |
| `app/state.py`, `app/store.py` | Модель стану й атомарне JSON-сховище |
| `app/main.py` | Веб-сторінка, API, валідація запитів і контрольовані HTTP-помилки |
| `eval/` | 20 звернень, runner порівняння й результати прогонів |

Власний набір звернень лежить у `eval/requests.json`. Порівняння workflow й агента можна запустити з цієї папки:

```powershell
.\.venv\Scripts\python.exe eval\run_eval.py --output eval\results.json
```

За замовчуванням скрипт виконує всі 20 звернень workflow й агентом по три рази, підтверджує дії workflow (крім одного тестового відхилення) і зберігає шлях, зміни магазину, відповідь, токени та час. Для перевірки відмов сервісу:

```powershell
.\.venv\Scripts\python.exe eval\run_eval.py --mode workflow --repeats 1 --failure-rate 0.3 --output eval\results-failure-30.json
```

Автоматичні перевірки коду:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Висновки фактичних прогонів наведено в [eval/findings.md](eval/findings.md).

## Чекліст самоперевірки

- [x] Workflow обробляє повернення, скасування і питання про стан замовлення; решта й незрозумілі звернення — уточнення або передача оператору.
- [x] Послідовність задає код; модель — лише на кроках, де потрібне розуміння мови; її вихід перевіряється схемою й змістом.
- [x] Дані магазину — інструментами з ПР8; клієнт — із сеансу; чуже замовлення не прочитати й не змінити.
- [x] Кожному кроку доступні лише його інструменти; дія зі змінами — тільки після підтвердження, і це забезпечує код.
- [x] Подвійне підтвердження, повторне звернення й перезапуск не створюють другої заявки; перед виконанням умови перевіряються ще раз.
- [x] Оператор бачить дію з аргументами й підстави; відхилення завершується відповіддю клієнтові.
- [x] Стан зберігається на диску; звернення, що чекає підтвердження, переживає перезапуск; статус змінюється лише дозволеними переходами.
- [x] Кожне звернення доходить до кінцевого стану; кроки, час і токени обмежено конфігурацією; причину зупинки видно на сторінці.
- [x] Відповідь клієнтові — за фактами зі стану й перевіряється кодом; службових даних у ній немає.
- [x] Текст звернення, адресований «системі», не змінює ходу обробки.
- [x] Застосунок не падає: збій моделі, недоступний сервіс, невалідний розбір дають контрольований стан, а не 500.
- [x] Межі модулів: модель — без магазину, інструменти — без API моделі, сховище — без моделі й магазину, веб-рівень — лише через workflow.
- [x] Ключ не потрапив ані в код, ані в репозиторій; каталог стану — теж.
- [x] Набір і щонайменше три власні звернення прогнано workflow й агентом по три рази; перезапуск, повтор, межі й відмови сервісу перевірено; висновки записано.
- [ ] Ви можете пояснити кожне ухвалене рішення.
